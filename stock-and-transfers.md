# Остатки, перемещения и списания — функциональная спецификация

> **Документ для согласования с руководством.** Описывает бизнес-процесс работы с регистром остатков на цехах, перемещениями между цехами и списаниями. Платформонезависимо — основа для реализации сначала в 1С, потом в Go-проекте MES.

---

## 1. Цель документа и область

### Что описывает

- **Регистр остатков** на цехах: что хранится, как считается, для какой номенклатуры.
- **Жизненный цикл заказа на выпуск (PO)**: статусы, переходы, что делается на каждом этапе.
- **Перемещения** между цехами: создание (из PO и свободное), приёмка, отмена.
- **Списания** номенклатуры с цеха (отдельная сущность).
- **Сценарии пользователя**: куда нажимает, какие диалоги, какие проверки.
- **Правила контроля наличия и блокировки** операций.
- **Права действий** по статусам и ролям.

### Что НЕ описывает (out of scope этого документа)

- Технические детали реализации (имена таблиц/полей в БД, API-эндпоинты).
- Внешний вид экранов (макеты UI).
- Загрузка справочников из 1С (это отдельный документ — `1c-load-api.md`).
- Kafka-интеграция с 1С (это отдельная подсистема, не пересекается с локальными остатками).
- Аналитика и отчётность по остаткам и перемещениям (отложено).
- Перерасчёт себестоимости (отдельная задача бухучёта).

### Контекст

Завод MES Kitchen: фабрика-кухня → производственные цеха → готовая продукция → магазины. Каждый цех имеет свой остаток номенклатуры. Заказы магазинов разворачиваются через BOM в заказы на выпуск (PO), которые распределяются по цехам. Цехи производят полуфабрикаты для других цехов и/или готовую продукцию.

## 2. Глоссарий

| Термин | Что значит |
|---|---|
| **СЕ (структурная единица)** | Фабрика-кухня, торговая точка, склад. Верхнеуровневая организационная единица. Например «ФК Алматы». |
| **Цех** | Производственная единица внутри СЕ. Например «Холодный цех», «Пекарня», «Овощной». У каждого цеха своя «корзина остатков». |
| **Номенклатура** | Товар, полуфабрикат или сырьё. Может быть с тех.картой (`expandable=true`) или без (`expandable=false`). |
| **П/ф** (полуфабрикат) | Номенклатура с активной тех.картой — мы её производим у себя. |
| **Сырьё** | Номенклатура без тех.карты — у нас не производится, поступает извне (мука, специи). |
| **Тех.карта (ТК)** | Рецептура: сколько каких ингредиентов идёт на единицу продукции. |
| **Заказ на выпуск (PO, release_order)** | Производственное задание: «цех X должен выпустить Y единиц номенклатуры Z к дате D». Создаётся через BOM-разузловку заказов магазинов. |
| **Регистр остатков** | Учётная система остатков по комбинации (номенклатура, цех). Аналог 1С `AccumulationRegister_ДвижениеТМЦ`. |
| **Перемещение** | Передача номенклатуры из одного цеха в другой. Двухстадийная: Передано → Принято. |
| **Списание** | Уменьшение остатка цеха без передачи в другой цех (порча, потери, корректировка). Отдельная сущность. |
| **Выпуск** | Действие: производственный цех произвёл порцию продукции, должна появиться на его остатке и (если есть потребители) уехать к ним. |

## 3. Регистр остатков — концепция

### 3.1 Что такое «остаток»

Остаток — это число: **сколько единиц номенклатуры N сейчас лежит в цехе W**. Ключ: пара `(номенклатура, цех)`. Все остатки независимы — одна и та же номенклатура в разных цехах хранится отдельно.

### 3.2 Откуда берутся изменения остатка

Остаток меняется в результате **проводок** (movements). Каждая проводка — это запись «в момент T в цехе W номенклатура N изменилась на +Q или -Q, причиной была операция X». Проводки append-only — не правятся, не удаляются.

**Типы проводок:**

| Тип | Когда возникает |
|---|---|
| `IN` (приход) | Цех произвёл выпуск; цех принял перемещение от другого цеха |
| `OUT` (расход) | Цех использовал ингредиенты при выпуске; цех передал перемещение в другой цех; списание |

### 3.3 Для какой номенклатуры ведётся регистр

**Для всей номенклатуры одинаково.** И для полуфабрикатов с ТК, и для сырья без ТК. Это сознательное решение — чтобы видеть полную картину «что и где сейчас лежит».

### 3.4 Контроль наличия — единственное различие между п/ф и сырьём

| Тип | Регистр ведётся? | Блокировка операций при нехватке? |
|---|---|---|
| Полуфабрикат с ТК (`expandable=true`) | ✅ Да | ✅ **Да** — нельзя начать выпуск/переместить если не хватает |
| Сырьё без ТК (`expandable=false`) | ✅ Да | ❌ **Нет** — минусовый остаток допустим (сырьё «вообще без приходов» — норма пока не появятся приходные документы) |

Минусовые остатки сырья — **сигнал к аналитике**, в UI подсвечиваются красным. Не блокируют работу.

### 3.5 Расчёт текущего остатка

Текущий остаток = сумма всех проводок (IN положительные, OUT отрицательные) по конкретной паре `(номенклатура, цех)`.

В реализации: используется агрегатная таблица `stock_totals` (последний пересчёт) + дельта `stock_changes` от последнего пересчёта. Это деталь реализации; пользователь и бизнес-логика работают с **«текущим остатком»** как с одним числом.

## 4. Жизненный цикл заказа на выпуск (PO)

Заказ на выпуск проходит через статусы:

```
Новый → Старт → (один или несколько Выпусков) → Готов
                                              ↓
                                          Отменён (любой статус)
```

| Статус | Что значит | Что происходит при переходе в этот статус |
|---|---|---|
| **Новый** | PO создан BOM-разузловкой, в производство не запущен | Запись в журнале (release_transactions). Никаких списаний. |
| **Старт** | Цех взял заказ в работу | **Никаких проверок остатков, никаких списаний.** Просто фиксация «начали работу». Можно при необходимости вернуть в Новый. |
| **Выпуск** (не статус, а действие — см. раздел 7) | Цех произвёл порцию продукции | Списание ингредиентов, создание перемещения для выпущенной партии. Может повторяться несколько раз для одного PO. |
| **Готов** | Финальный выпуск, заказ закрыт. `actual_qty` = сумма выпусков | Аналогично «Выпуск» — последняя итерация. После этого PO нельзя продолжать. |
| **Отменён** | Заказ снят с производства | Уже сделанные выпуски не откатываются (их откатывают руками через отмены перемещений). |

### Пример полного жизненного цикла

PO: «Цех Теста выпустить 50 кг теста для Круассан (нужно 30) и Пельмени (нужно 20)».

1. **Новый** → BOM создал PO.
2. **Старт** → повар нажал «Взять в работу». Никаких изменений в остатках.
3. **Выпуск 1**: повар замесил 20 кг (частично).
   - Списываются ингредиенты (мука, вода, ...) с остатка Цеха Теста.
   - 20 кг теста должны уехать к Круассану (30) и Пельменям (20) — общая потребность 50, выпустили 20. **Не покрывает** → диалог распределения. Пользователь решает: 12 кг → Круассан, 8 кг → Пельмени.
   - Создаётся перемещение (batch) с 2 строками.
4. **Выпуск 2**: повар замесил ещё 30 кг.
   - Снова списание ингредиентов.
   - Расчёт остаточной потребности: Круассану нужно ещё 30-12=18, Пельменям ещё 20-8=12. Сумма = 30. Выпустили 30 — **покрывает**. Без диалога: 18 → Круассан, 12 → Пельмени.
   - Создаётся перемещение (batch) с 2 строками.
5. **Готов** — последний шаг подтверждён. `actual_qty` PO = 50.

## 5. Структура хранения «Перемещение»

### 5.1 Концепция

Все перемещения хранятся в **одной таблице**. Один логический акт перемещения (одно нажатие пользователя «Создать перемещение») может породить **несколько строк** этой таблицы — например, когда выпуск распределяется между несколькими цехами-получателями. Эти строки объединяются общим `batch_id`.

### 5.2 Поля таблицы перемещений

| Поле | Тип | Назначение |
|---|---|---|
| `batch_id` | UUID | Идентификатор «пачки» — группы строк одного логического перемещения |
| `row_id` | UUID | Идентификатор конкретной строки (PK таблицы) |
| `sender_workshop_id` | UUID | Цех-отправитель |
| `recipient_workshop_id` | UUID | Цех-получатель |
| `nomenclature_id` | UUID | Что перемещаем |
| `quantity` | NUMERIC | Сколько перемещаем |
| `created_at` | TIMESTAMP | Когда создали (= `now()` в момент создания) |
| `created_by` | UUID | Пользователь, создавший перемещение |
| `release_order_id` | UUID NULL | PO, на основании которого создано (NULL для свободных перемещений) |
| `status` | ENUM | `Передано` (по умолчанию), `Принято`, `Отменено` |
| `accepted_at` | TIMESTAMP NULL | Когда получатель принял |
| `accepted_by` | UUID NULL | Кто из получателей подтвердил |
| `actual_quantity` | NUMERIC NULL | Фактическое количество (может отличаться от `quantity` если в приёмке скорректировали) |
| `cancelled_at` | TIMESTAMP NULL | Когда отменено |
| `cancelled_by` | UUID NULL | Кто отменил |
| `cancellation_reason` | TEXT NULL | Комментарий при отмене (опц.) |

### 5.3 Статусы строки

```
Передано ──→ Принято
   │            │
   │            └──→ Отменено (только отправителем — возврат МЦ)
   │
   └──→ Отменено (отправитель или получатель)
```

| Статус | Описание |
|---|---|
| **Передано** | Создано отправителем, **сигнал получателю** что нужно забрать. **Остаток у отправителя ещё НЕ списан** — продукция физически у него до момента приёмки. |
| **Принято** | Получатель подтвердил приёмку. В этот момент **атомарно**: `OUT` у отправителя + `IN` у получателя. |
| **Отменено** | Перемещение отменено. Никаких эффектов на остатки откатывать не надо (их и не было). |

> **Важно:** хотя остаток формально не списан, продукция **зарезервирована** для этого перемещения. При создании нового перемещения система проверяет «доступное к перемещению» = `stock_totals − сумма qty всех непринятых исходящих "Передано"`. Это предотвращает двойную передачу одной и той же продукции (см. раздел 13).

## 6. Структура хранения «Списание»

Списание — это операция уменьшения остатка цеха **без** перевода в другой цех. Например, продукция испортилась, переучёт показал недостачу, технологические потери.

### 6.1 Концепция

Аналогично перемещениям, списания хранятся в одной таблице с группировкой через `batch_id` (одно нажатие «Создать списание» может породить несколько строк).

### 6.2 Поля таблицы списаний

| Поле | Тип | Назначение |
|---|---|---|
| `batch_id` | UUID | Группа строк одного списания |
| `row_id` | UUID | PK строки |
| `workshop_id` | UUID | Цех, с которого списываем |
| `nomenclature_id` | UUID | Что списываем |
| `quantity` | NUMERIC | Сколько списываем |
| `created_at` | TIMESTAMP | Когда оформлено |
| `created_by` | UUID | Кто оформил (создатель документа) |
| `release_order_id` | UUID NULL | PO, на основании которого создано (NULL для свободных списаний) |
| `cost_article_id` | UUID | **Статья затрат** (справочник причин: «технологические потери», «брак», «корректировка переучёта»). Заменяет отдельное поле «причина» — статья и есть причина. |
| `comment` | TEXT NULL | Свободный комментарий (почему списали, обстоятельства) |
| `document_attachment_url` | TEXT NULL | Привязка к документу-основанию (акт, фото). Обязательно при списании типа «брак при выпуске», иначе опционально. |
| `responsible_user_id` | UUID NULL | Ответственный сотрудник (если отличается от создавшего — например, диспетчер оформил со слов кладовщика). |

### 6.3 Статусы

Одностадийное действие: создано — применено. Acceptance-workflow как у перемещений не нужен — никто не «принимает» списание.

## 7. Сценарий: «Создать перемещение из PO»

### 7.1 Где кнопка

В карточке заказа на выпуск (PO). Доступна когда:
- PO в статусе **Старт** (или дальше — частичные выпуски).
- По PO есть **выпущенное, но ещё не переданное** количество. То есть `выпущено − уже_перемещено > 0`.

Если PO ещё `Новый` или вся выпущенная партия уже передана, кнопка **неактивна**.

### 7.2 Контекст автоматически известен

При нажатии система сама определяет:
- **Отправитель (sender_workshop_id)** = цех PO.
- **Номенклатура** = номенклатура продукции PO.
- **Доступное количество** = текущий остаток номенклатуры в цехе PO (= выпущено − уже перемещено).
- **Список получателей** = из плана (`release_order_sources`): какие потребители (другие PO или прямые заказы магазинов) и сколько каждому ещё нужно (с учётом уже отправленного).
- **Время** = `now()`.

### 7.3 Логика — 4 случая

Поведение зависит от двух факторов: число цехов-получателей (1 или несколько) и хватает ли выпуска на потребность всех.

| Случай | Цехов-получателей | Покрывает потребность | Что видит пользователь |
|---|---|---|---|
| **A** | 1 | Любое (полное/частичное) | Без диалога. Сразу создаётся 1 строка перемещения: всё доступное → этому единственному получателю. |
| **B** | 2+ | **Полное** (хватает всем) | Без диалога. Автоматически 1 строка на каждого получателя — каждому ровно столько, сколько ему нужно по плану. |
| **C** | 2+ | **Частичное** (не хватает всем) | **Диалог распределения**. Показывает список получателей с плановой потребностью + поле ввода факт. количества на каждого. По умолчанию заполнен алгоритмом ниже. Пользователь может перекинуть руками. Сумма должна равняться доступному. |
| **D** | 0 | — | Кнопка недоступна (PO без потребителей не должен возникать — это баг BOM). |

#### Алгоритм дефолтного распределения для случая C

Берётся из `release_order_sources` текущего PO, сортируется и заполняется по приоритету:

```
sources = release_order_sources WHERE release_order_id = current_PO.id
sortBy:  level DESC, plan_date ASC, created_at ASC, line_number ASC
remaining = доступное_к_перемещению
для каждого src в отсортированных sources:
    нужно_этому = src.quantity − уже_передано_этому_получателю
    дать = min(remaining, нужно_этому)
    default[src] = дать
    remaining -= дать
    если remaining == 0: break
```

**Почему `level DESC` первичная сортировка:**
- `level` — глубина потребителя в BOM-дереве.
- Чем больше `level` (внутренний PO глубже по цепочке) — тем критичнее обеспечить его ингредиентами, иначе встанет вся цепочка наверх.
- Магазин (`level=1` после миграции 000014) — последний по приоритету: получит остаток, или будет недопоставка, которая закроется со следующего выпуска.

**Внутри одного уровня** сортировка по `plan_date ASC` (раньше нужно — раньше получает), при равной дате — `created_at ASC` (FIFO по созданию документа), при полном совпадении — `line_number ASC`.

### 7.4 Что создаётся в БД при подтверждении

В одной транзакции:

1. Создаются N строк перемещения (по числу выбранных получателей) с общим `batch_id`. Каждая строка:
   - `sender_workshop_id` = цех PO
   - `recipient_workshop_id` = выбранный цех-получатель
   - `nomenclature_id` = из PO
   - `quantity` = распределённое количество
   - `release_order_id` = ID этого PO
   - `status` = `Передано`
   - `created_at` = `now()`
   - `created_by` = текущий пользователь
2. **Никаких `OUT`-проводок** у отправителя в этот момент **не делается** (см. раздел 12 — списание происходит только при приёмке).

### 7.5 Проверки и блокировки

- Кнопка неактивна если нет доступного выпуска (см. 7.1).
- В диалоге сумма распределения должна равняться доступному количеству (не больше, не меньше).
- Нельзя выбрать получателя который не в списке плановых потребителей. Если нужно «отдать постороннему» — использовать **свободное перемещение** (раздел 9).

## 8. Сценарий: «Создать списание из PO»

### 8.1 Где кнопка

В карточке PO, рядом с «Создать перемещение». Доступна когда:
- В цехе PO есть остаток номенклатуры этого PO (= выпущено − уже перемещено − уже списано > 0).

### 8.2 Контекст из PO

- `workshop_id` = цех PO
- `nomenclature_id` = номенклатура PO
- `release_order_id` = ID PO

### 8.3 Диалог

Пользователь указывает:
- Количество для списания (≤ доступного).
- **Статья затрат** (выпадающий список из справочника — обязательное).
- Прочие поля — согласовать (см. раздел 15).

### 8.4 Что создаётся

В одной транзакции:
- 1 строка списания (одна номенклатура — один `row_id`, `batch_id` = `row_id` или отдельный — по соглашению).
- Соответствующая проводка `OUT` в регистре остатков.
- Уменьшение `stock_totals` на доступное количество цеха.

## 9. Сценарий: «Свободное перемещение» (без PO)

### 9.1 Где UI

Отдельный экран **«Список перемещений»** в админ-зоне MES или в зоне руководителя цеха. На нём кнопка «Создать перемещение».

### 9.2 Диалог

1. Выбор цеха-отправителя (по умолчанию — цех текущего пользователя).
2. Выбор цеха-получателя (любой из существующих).
3. **Подбор номенклатуры**: список текущих остатков цеха-отправителя с поиском. Пользователь может выбрать одну или несколько позиций.
4. Для каждой позиции — количество (≤ остатка в цехе-отправителе).
5. (опционально) комментарий.

Можно добавить несколько строк (разные номенклатуры) — все попадут в один `batch_id`.

### 9.3 Что создаётся

Аналогично 7.4, но `release_order_id = NULL`.

### 9.4 Проверки

Для каждой строки:
- Для **п/ф с ТК** — `quantity` ≤ остатка цеха-отправителя (блокировка).
- Для **сырья без ТК** — без блокировки, минусы допустимы.

## 10. Сценарий: «Приёмка перемещения»

### 10.1 Где UI

Экран «Входящие перемещения» цеха-получателя. Виден руководителю цеха-получателя. Список строк перемещений где `recipient_workshop_id` = текущий цех и `status` = `Передано`.

### 10.2 Действия по строке

- **Принять (Принято)** — основное действие.
- **Принять с уточнением фактического количества** — кладовщик мог пересчитать и обнаружить расхождение.
- **Отменить (Отменено)** — отказ.

### 10.3 Что происходит при подтверждении «Принято»

В одной транзакции:
- `status` → `Принято`.
- `accepted_at` = `now()`, `accepted_by` = пользователь.
- `actual_quantity` = указанное фактическое (или = `quantity` если без уточнения).
- Проводка `OUT` у отправителя (если ещё не списано — см. раздел 12 про момент списания).
- Проводка `IN` у получателя.
- Соответствующие обновления `stock_totals`.

### 10.4 Что происходит при «Отменено»

- `status` → `Отменено`.
- `cancelled_at`, `cancelled_by`, опц. `cancellation_reason`.
- Если уже было списано у отправителя — возврат `IN` отправителю (компенсирующая проводка).
- У получателя ничего не появляется (он же не принимал).

## 11. Сценарий: «Отмена перемещения»

### 11.1 Из статуса `Передано`

Отменить может **отправитель** или **получатель**. Никаких остатков ещё не двигалось у получателя — только списание у отправителя могло пройти (см. раздел 12). При отмене — возврат у отправителя через компенсирующую `IN`-проводку.

### 11.2 Из статуса `Принято`

Отменить может **только отправитель** (бизнес-кейс «вернуть назад товар после приёмки»). Технически это:
- `OUT` у получателя
- `IN` у отправителя
- `status` → `Отменено`

Получатель сам отменить из `Принято` **не может** — это уже его материал.

## 12. Атомарность операций — псевдокод транзакций

### 12.1 Создание перемещения (из PO или свободное)

**Списание остатка НЕ происходит** — только фиксация намерения. Но проверяется
«доступное к перемещению» (см. раздел 13), чтобы не передать дважды.

```
BEGIN
  для каждой строки перемещения:
      проверка доступного к перемещению:
          available = stock_totals.qty(sender, nom)
                    - SUM(qty) из всех transfer_rows
                      WHERE sender_workshop=sender AND nom=nom AND status='Передано'
          если nomenclature.expandable = true И available < quantity:
              ROLLBACK
              ошибка пользователю: "недостаточно доступного для перемещения ..."
      INSERT transfer_row (batch_id, row_id, sender, recipient, nom, qty, status='Передано', ...)
      -- НИКАКИХ stock_movement / stock_totals операций!
      -- Остаток у отправителя НЕ списывается до приёмки.
COMMIT
```

### 12.2 Приёмка перемещения

В этот момент происходит **реальное движение остатков** — атомарно у обоих цехов.

```
BEGIN
  UPDATE transfer_row SET status='Принято', actual_quantity=Q, accepted_at=now(), accepted_by=user
  -- В одной транзакции списываем у отправителя и принимаем у получателя:
  INSERT stock_movement (OUT, sender_workshop, nom, qty=actual_quantity, registrar=transfer_row)
  UPDATE stock_totals SET qty -= actual_quantity WHERE (sender, nom)
  INSERT stock_movement (IN, recipient_workshop, nom, qty=actual_quantity, registrar=transfer_row)
  UPDATE stock_totals SET qty += actual_quantity WHERE (recipient, nom)
COMMIT
```

**Если `actual_quantity ≠ quantity`** (получатель уточнил факт при приёмке): списываем у отправителя и приходуем у получателя именно `actual_quantity`. Разница остаётся у отправителя как «непереданное».

### 12.3 Отмена из статуса `Передано`

Никаких компенсирующих проводок не нужно — остаток ещё не двигался.

```
BEGIN
  UPDATE transfer_row SET status='Отменено', cancelled_at, cancelled_by, cancellation_reason
  -- Никаких stock_movement / stock_totals — их и не было.
COMMIT
```

После этой операции отправитель снова видит эту продукцию в «доступном к перемещению».

### 12.4 Отмена из статуса `Принято` (только отправитель)

Здесь движение уже было — нужны компенсирующие проводки.

```
BEGIN
  UPDATE transfer_row SET status='Отменено', cancelled_at, cancelled_by, cancellation_reason
  -- Возврат: уменьшаем у получателя, увеличиваем у отправителя
  INSERT stock_movement (OUT, recipient_workshop, nom, qty=actual_quantity, registrar=transfer_row)
  UPDATE stock_totals SET qty -= actual_quantity WHERE (recipient, nom)
  INSERT stock_movement (IN, sender_workshop, nom, qty=actual_quantity, registrar=transfer_row)
  UPDATE stock_totals SET qty += actual_quantity WHERE (sender, nom)
COMMIT
```

### 12.5 Создание списания

```
BEGIN
  для каждой строки списания:
      проверка наличия (см. раздел 13 — учитывает настройки allow_negative_stock_*):
          если требуется блокировка И доступное_к_списанию < quantity:
              ROLLBACK
              ошибка
      INSERT writeoff_row (...)
      INSERT stock_movement (OUT, workshop, nom, qty, registrar=writeoff_row)
      UPDATE stock_totals SET qty -= quantity WHERE (workshop, nom)
COMMIT
```

## 13. Правила контроля наличия

### 13.1 Понятие «доступного к операции» количества

Поскольку при создании перемещения остаток у отправителя ещё не списывается (списание происходит только при приёмке — см. раздел 12), нужна концепция **«доступного»** количества, отличного от просто остатка:

```
доступное_к_перемещению(sender, nom) =
    stock_totals.qty(sender, nom)
    − SUM(qty) всех transfer_rows
       WHERE sender_workshop = sender
         AND nomenclature   = nom
         AND status         = 'Передано'   -- ещё не принято и не отменено
```

То есть из текущего остатка вычитается **всё, что уже отправлено, но ещё не принято** — эта продукция «зарезервирована» под висящие перемещения и не может быть перемещена/списана повторно.

То же для списания:
```
доступное_к_списанию(workshop, nom) =
    stock_totals.qty(workshop, nom)
    − SUM(qty) исходящих transfer_rows со status='Передано'
```

### 13.2 Глобальные настройки контроля

Контроль наличия управляется записями в таблице `settings` (key-value со столбцом описания):

| Ключ | Значение | Что значит |
|---|---|---|
| `allow_negative_stock_pf` | `false` (по умолчанию) | Запретить отрицательные остатки по полуфабрикатам (`expandable=true`). При попытке операции, которая загонит в минус — блокировка с ошибкой. |
| `allow_negative_stock_ingredient` | `true` (по умолчанию) | Разрешить отрицательные остатки по сырью без ТК (`expandable=false`). Операция не блокируется, остаток уходит в минус. В UI подсвечивается красным. |

**Решение «блокируем / не блокируем»** = посмотреть `expandable` ингредиента и взять соответствующую настройку:

```
блокировать = (expandable=true  И allow_negative_stock_pf         = false)
           ИЛИ (expandable=false И allow_negative_stock_ingredient = false)
```

В дефолтной конфигурации: п/ф блокируем, сырьё нет. Админ может переключить если бизнес требует иначе.

#### Откуда берутся дефолтные значения

Таблица `settings` создаётся миграцией, которая **в той же транзакции** наполняется дефолтными значениями всех ключевых настроек:
- `allow_negative_stock_pf` = `false`
- `allow_negative_stock_ingredient` = `true`
- `stock_recalc_mode` = `realtime`

То есть после развёртывания свежей БД и наката миграций таблица **уже наполнена** — приложение всегда найдёт нужные значения. Пустая `settings` после установки — **баг развёртывания**, не норма. Приложение должно явно ругаться при чтении отсутствующего ключевого ключа.

**Правило проекта:** при добавлении новой настройки в будущих миграциях — **обязательно** включать `INSERT` с дефолтом в той же миграции, в которой настройка вводится. Никаких «отдельных seed-скриптов» или «добавим вручную после установки».

### 13.3 Таблица проверок

| Когда | Что проверяем | Действие при нехватке |
|---|---|---|
| Создание перемещения (из PO или свободного) | `доступное_к_перемещению(sender, nom) ≥ quantity` при условии что номенклатура контролируется (см. 13.2) | Блокировка с сообщением «недостаточно доступного к перемещению» |
| Создание списания | `доступное_к_списанию(workshop, nom) ≥ quantity` при условии что номенклатура контролируется | Блокировка |
| Приёмка перемещения | Не блокируем приём по нехватке у отправителя — это уже его проблема. Если по факту вдруг нечего передавать — отправитель отменяет перемещение, а не получатель блокируется. | — |
| Старт PO | **Никаких проверок.** Просто смена статуса. | — |
| Выпуск (любой) | Проверка наличия ингредиентов: для каждого контролируемого ингредиента — `доступное_к_списанию(цех_PO, ингредиент) ≥ требуется_на_выпуск` | Блокировка |

**Минусовые остатки** (когда настройка `allow_negative_stock_*` = `true` и операция уходит в минус) — **сигнал к аналитике**, в UI подсвечиваются красным. Работу не блокируют.

## 15. Принятые решения и открытые вопросы

### 15.1 ✅ Момент списания у отправителя при перемещении

**Решено:** списание происходит **только при приёмке** получателем. До приёмки остаток у отправителя НЕ списывается — он физически у него. Статус `Передано` = просто сигнал получателю «нужно забрать».

Чтобы избежать двойной передачи одной и той же продукции — введена концепция «доступного к перемещению» (раздел 13.1): из текущего остатка вычитаются висящие исходящие `Передано`-строки.

### 15.2 ✅ Цех-склад готовой продукции

**Решено:** всегда **один** цех-склад ГП на СЕ. Поле `finished_goods_workshop_id` в справочнике структурных единиц однозначно определяет куда уезжает готовая продукция.

### 15.3 ✅ Связка с 1С (бухучёт)

**Решено:** на текущем этапе **не выгружаем** проводки перемещений/списаний обратно в 1С. Учёт ведём только у себя. Если в будущем потребуется — обсуждаем механизм отдельно.

### 15.4 ✅ Момент пересчёта `stock_totals`

**Решено:** управляется глобальной настройкой `stock_recalc_mode` в таблице `settings` со значениями:
- `realtime` — после каждой проводки `stock_totals` обновляется немедленно.
- `cron` — `stock_changes` копит дельту, ночной job переносит в `stock_totals`.

По умолчанию ставим `realtime` (самый простой и безопасный). Админ может переключить если появится нагрузка. Гибридный режим отменён — слишком сложен в эксплуатации.

### 15.5 ✅ Состав поля «Списание»

**Решено** (см. раздел 6.2). Помимо обязательной `cost_article_id` (которая и есть «причина»):
- `comment` — свободный комментарий, всегда опционален.
- `document_attachment_url` — привязка к документу. Обязательна при списании типа «брак при выпуске», иначе опциональна.
- `responsible_user_id` — ответственный, если отличается от создавшего.

Полей «подтверждающий» и «дата задним числом» не делаем.

### 15.6 ✅ Алгоритм распределения в диалоге частичного выпуска

**Решено** (см. раздел 7.3): по умолчанию заполняется по приоритету `level DESC`, при равном уровне — `plan_date ASC`, `created_at ASC`, `line_number ASC`. Это даёт приоритет внутренним производственным цепочкам перед магазином. Пользователь может перекинуть руками.

### 15.7 ✅ Уровни BOM — миграция выполнена

**Решено и сделано** 2026-05-18: миграция `000014_bom_level_shift_plus_one` накатана. Уровни BOM теперь нумеруются с 1 (как в 1С): goods_order source = `level=1`, top-level PO = `level=2`, ингредиенты = `level=3+`. Это часть общего принципа «бизнес-логика и алгоритмы идентичны 1С».

## 16. Что НЕ входит в scope этой реализации

Перечислено явно чтобы не было путаницы:

1. **Резервы под конкретный заказ на выпуск** (`stock_reservations`) — концепция отменена. Достаточно общего остатка на цехе.
2. **Перерасчёт себестоимости** — отдельная задача бухучёта, делается на стороне 1С.
3. **Складской учёт по партиям FIFO/LIFO** — у нас нет партий, остаток — одно число на (номенклатура, цех).
4. **Учёт мест хранения внутри цеха** — нет, цех = одна «корзина».
5. **Учёт по контрагентам/партнёрам** — нет, всё внутри одной фабрики.
6. **Расширенная аналитика и BI-отчёты** — отдельная задача, не блокирует основной функционал.
7. **Прогноз остатков на будущее** — нет, только текущее состояние.
8. **Управление приходами от поставщиков** — пока не реализовано, сырьё «появляется из ниоткуда» (минусы). Когда появятся приходные документы, регистр пополнится без изменений в этой логике.
